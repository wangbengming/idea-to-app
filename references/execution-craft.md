# 执行与推理手册（防"想得浅、动手松"）

本手册是全班组的**第三册**（前两册：`design-baseline.md` 防丑、`design-craft.md` 产美）。它治的不是"哪一科不懂"，而是三个跨岗位的通病：

> 1. **想得浅**——带着没说出口的假设动手（"用户肯定用大屏""输入肯定是干净的"），假设错了，后面全错；
> 2. **说得虚**——验收与测试用虚词写（"体验流畅""操作简便"），没法判对错，也就没法打回；
> 3. **查得松**——自己写的东西自己查，思路同源盲区相同，正向走一遍"能用"就交差，没人**专门去找坏**；
> 4. **写得乱**——没想清状态和数据流就敲代码，改一处坏一处，功能"都有"但互相打架。
>
> 典型事故：小工具类项目"样式拉跨、操作繁琐、小毛病一堆"——三件事分别对应：设计机制在小项目路径被跳过（第〇节补）、没有操作成本概念（第四节）、没有对抗审查（第三节）；"功能都在但逻辑拧巴"对应第六节逻辑工艺。

---

## 〇、全岗位适用：动手前的三个动作（5 分钟）

1. **写假设**：把三个最要命的隐含假设写在产出文档开头"假设"行（例：用户用手机/字段不多于 10 个/用户识字无障碍）。假设写出来才会被检验——孕妈助手类项目最常见的翻车，就是按"年轻人、大屏、打字快"设计了一个孕妈产品。
2. **定阈值**：每条要验收的话里必须有数字（见第二节虚词黑名单）。
3. **想好怎么验**：写完就知道拿什么动作、几步、看到什么算过。

**体验三问（每条功能动笔前问一遍——AC 是底线不是上限）**："只实现需求"做不出好用的东西，每条功能在写 AC 与写代码之前，先答这三问并把答案落进产出文档：

1. **用户做完这一步，下一步是什么？**——功能之间要接得上（记完账→看到本月合计；下单→知道多久送到）。答不上来说明只做了孤岛功能，把"下一步"补成需求。
2. **等待、出错、空数据时，用户看到什么？**——三态不是装饰，是功能的一半；loading 骨架、错误怎么办、空态引导，写 AC 时就带上（见第六节与 design-baseline）。
3. **用户为什么会再打开它？**——回访理由（数据在涨/进度在推进/顺手）想清楚，才知道第一版该把哪一口气做足。

三问答完，至少给每条核心功能补 1 条**体验类 AC**（完成反馈/三态/可撤销/连贯到下一步），和功能类 AC 一起进验收。

## 一、逼问式决策锁定（动手前过问题清单）

各岗位动笔前过一遍自己的问题清单，**一问一句答案，写进产出文档**；答不上来的问题就是窟窿——**带窟窿不许动工**（kill 准则）：触发红线问题就停下来退回/问用户，不许"先做着后面再说"。

| 岗位 | 动笔前必答 | 红线（触发即停） |
|---|---|---|
| 产品经理 | ① 用户的一件事是什么、10 秒内能完成吗？② 用户在什么场景/设备/状态下用？③ 这个功能不做会死吗？④ 用户怎么知道"我做成了"？⑤ 谁会第一次打开就放弃，为什么？⑥ 体验三问答了吗——做完这步下一步是什么/等待出错空数据时看到什么/为什么会再打开（第〇节）？⑦ 深挖三层到了吗——表面诉求之下的真实动机、隐含期待、反需求都列了吗（特色节的隐含期待清单）？⑧ 流程节点问穿了吗——每个流程逐节点过六问（入口/做什么/反馈/去向/异常/数据），答案有来源（用户原话/假设标注/调研），没有想当然的空白？ | 核心动说不清 / AC 写不出数字 |
| 设计师 | ① 3 个气质形容词是什么？② 用户最不满意的上一个同类东西长什么样？③ 高频动作的操作成本是几次点击/几个字段？④ 画像最弱的那位用户能用吗？ | 风格族选不出 / 高频动作超预算 |
| 技术负责人 | ① 数据量多大、涨到 10 倍会怎样？② 双击打开的环境里什么做不到（对照能力边界表）？③ 出错时用户看到什么？④ 逻辑架构四表（状态/数据流/边界/分层）落 03 了吗？ | 能力边界表命中做不到的功能 |
| 开发 | ① 02 的令牌值抄进 :root 了吗？② 每个可点元素的五个状态都有吗？③ 空态/错态/加载都实现了吗？④ 最坏输入（空/超长/特殊字符/连点）会怎样？⑤ 每份界面状态是不是只存一处、改状态后是不是只有一条渲染路径（第六节单向数据流）？ | 样式出现令牌外裸值 |
| 测试 | ① 每条 AC 的可测试问句是什么？② 破坏性输入清单列了吗？③ 哪些问题只有真机点才能发现（列给 PMO）？ | 用例全部是正向路径 |

## 二、可验证阈值：虚词黑名单与转换表

**黑名单**（出现在 AC / 用例 / 走查结论里 = 打回）：体验好、流畅、美观、简便、快速、稳定、合理、友好、完善、优化。

**转换表**（虚词 → 可判对错）：

| 虚词说法 | 可验证说法 |
|---|---|
| 记一笔要简便 | 新增一笔 ≤ 2 次点击、0 个必填文本框（点数字按钮即存） |
| 操作不繁琐 | 5 个高频动作各自的点击/输入步数列入预算表且全部达标 |
| 页面好看 | 全站样式只出现 02 令牌值；走查对抗审查无"外观"类发现 |
| 加载快 | 本地打开 2 秒内可交互（双击 → 能点第一个按钮） |
| 提示友好 | 每个错误提示含"哪里错 + 怎么改"；空状态有一个明确按钮 |
| 适合孕妈用 | 正文 ≥ 18px、按钮 ≥ 48px 高、单手拇指区可达、无拼音缩写 |

## 三、对抗式三人格审查（治"小毛病一堆"）

自审的同源盲区：写的人和查的人共享同一套假设，正向走一遍觉得"没问题"。**破解法：换人格专门找坏。** 三个固定人格，按场景选用（开发提测前自审、QA 测试、PMO 走查都用）：

| 人格 | 心态 | 专找什么 |
|---|---|---|
| **破坏者** | "我要把它弄坏" | 最坏输入（空/超长/特殊字符/负数/连点/断网/中途返回）；连点两次会怎样？这一步做一半退出会怎样？ |
| **笨用户新手** | "第一次用、不看说明、按直觉乱点" | 第一眼知不知道该点哪？点错了能回去吗？提示是术语吗？空状态知道干嘛吗？ |
| **隐私官** | "这份数据泄露了会怎样" | 收了没必要收的吗？导出/删除路在哪？明文/密文？偷偷联网吗？ |

**加一问·未来骂声（预演失败，零疏漏扫描，提测前必答）**：三个人格找的是"做错的"，这一问找的是"没想到的"——假设三个月后用户在骂这个应用，最可能骂的是哪三条？（换台电脑数据看不了？某一步总是点错？导出的文件别人打不开？数据涨十倍卡死？入口找不到？）逐条处置：现在就修，或列入"以后再说"并在交付时告知用户"现在有个局限是 X"。**找不出骂声 = 没扫够，回去再想**；三条全落在"做错的"层面 = 把预演失败用成了三人格，重来。

**纪律（照做，不许打折）：**
1. **每人必须至少报 1 条**——找不到 = 没找够，回去再找；实在无懈可击，写出你最没把握的那条假设；
2. 不许和稀泥（"这里可能有点小问题不过还好"）——要么是要修的，要么闭嘴；
3. **双命中升级**：两个及以上人格抓到同一个问题，严重度升一级；
4. 报问题带三件套：**现象（哪一步）+ 后果（用户会遇到什么）+ 修法（具体怎么改）**；
5. 输出判决：**BLOCK**（有 1 条"孕妈用不了"级 → 修复前不许提测/发版）/**CONCERNS**（无阻断但有 2+ 条应修 → 修完再交）/**CLEAN**（只有记录级建议）。

## 四、操作成本预算（治"操作繁琐"）

交互是有价格的，价格单位是**点击次数、输入字段数、等待秒数**。02 的「交互」节必须给高频动作列预算表，走查对表审计：

| 动作类型 | 预算上限 | 超了怎么办 |
|---|---|---|
| 最高频动作（记账/打卡/开始） | ≤ 2 次点击、0 个必填文本框 | 做成大按钮/数字键盘/一键默认 |
| 高频动作（改状态/筛选） | ≤ 3 次点击 | 给默认值，常用项前置 |
| 低频动作（设置/备份/删改） | ≤ 5 次点击，允许藏深 | 收进次级入口 |
| 表单 | 必填字段 ≤ 5 个；能选不打字、能默认不问 | 拆步、给示例、给默认 |
| 任何等待 | ≥ 1 秒必须有进度反馈，≥ 5 秒必须可中断 | 骨架屏 + 取消按钮 |

**默认值策略**：每个可填字段问一句"90% 的情况填什么"——把答案做成默认值。用户改默认值的成本，远低于每次从零填。

## 五、严重度定级与优先排序

QA 定级用四级（写入 bug 单时映射回固定格式"严重/一般/建议"）：

| 级 | 名 | 判据 | 动作 |
|---|---|---|---|
| 4 | 阻断 | 用户完不成核心任务 / 数据丢失 / 安全问题 | BLOCK，修复前不发 |
| 3 | 重 | 核心任务能完成但有明显磕绊、错误频出 | 发版前必修 |
| 2 | 轻 | 造成犹豫/困惑，但能自己绕过 | 尽快修 |
| 1 | 记录 | 观感与打磨问题 | 排队 |

多条问题排序用 **优先分 = 频率 × 严重度 × 可解性**（各 1~5，乘积大者先修）——防"捡软柿子修"，也防"为个别人吹毛求疵"。

## 六、逻辑工艺（治"写得乱"——动手前 10 分钟，代码少返工一半）

"逻辑混乱"几乎从不是算法问题，而是**没定状态和数据流就开写**：同一份数据 DOM 里一份、变量里一份、事件里又改一份，改一处漏三处。技术负责人把它落进 03「逻辑架构」，开发照它写；单文件小工具也在文件头用注释写迷你版。**逻辑四表**：

1. **状态清单**：应用有哪些会变的东西（数据 + 界面状态如"当前 tab/加载中"），每项写：谁持有、初值、谁允许改。**每份状态只存一处**——真状态在数据对象里，DOM 只是它的投影；"从界面读回来当数据用"是混乱的起点。
2. **单向数据流**：事件 → 改状态 → 整体重渲染（或明确声明局部更新）。禁止事件之间互相触发链式 DOM 修补；"当 X 变就改 Y"超过 3 层说明该换响应式方案（tech-recipes 引入阶梯 L3）。
3. **边界与异常路径**：每个输入列最坏值（空/超长/特殊字符/负数/超范围日期）和对应行为；每个等待列超时表现；每个外部资源列失败表现。行为写"提示什么 + 状态回到哪"，不许"假定不会发生"。
4. **分层组织**：数据层（存取）/ 业务规则（纯函数，不碰 DOM）/ 渲染（只读状态画界面）/ 事件绑定（只翻译交互为状态变更）。单文件也用注释分节隔开；能被 06 自查和测试单独调用的是好分层。
5. **拓展点**：对照 PRD 的需求域延展路线（「以后再说」里的能力），第一版不做但**架构留生长点**——数据表可加列可加表（建表带版本/迁移思路）、路由与功能模块可插（照骨架 route 模式加不动既有结构）、处理管线可挂环节（如导出管线预留字幕轨）——不留死胡同；确实绕不开的死胡同，在 03 写明将来怎么破与代价。

**代码纪律**（评审与走查照此打回）：函数只做一件事，超过一屏先拆；分支用早返回拍平，不套三层 if；魔法数字进令牌或常量并命名；渲染出口唯一——同类列表只有一个渲染函数；删除类操作先想"能不能撤销"（见 design-baseline 交互节）再想"怎么确认"。**体感与事件纪律**（tech-recipes 体感工艺节）：事件处理 ≤16ms 内让出主线程（长活分片/异步）；事件绑定写在 JS，**innerHTML 里拼 onclick = 逻辑违例**；`confirm`/`alert`/`prompt` 当正式交互 = 违例；点击必须同帧先出反馈态。

## 七、复发性问题根因纪律（治"同一个需求反反复复"）

同一诉求或 bug **第二次**出现就不是新问题，是上一次没修断根。动修之前先过**根因三问**：① 这是第几次？同一个点还是同一类？② 上次修在哪一层（需求没问清 / 设计没接住 / 实现走样 / 架构不支持），为什么没断根——修了表面还是没回改上游？③ 这次修在哪一层才能断根——修在根因层，同层的同类问题**连带清一遍**，不逐个打补丁。

纪律：修在上游层的必须同步回改对应文档（需求层回改 PRD 重过 G1、样式走样回改 02 令牌、结构混乱回改 03 逻辑架构）——**只改代码不改文档 = 下次必复发**。同一问题出现第三次 = PMO 亲自接管按根因层重构，并在《05-发布记录》留"复发根因"一行。

## 八、执行循环（执行层工作法——小步真跑，不盲写）

产出质量的一半取决于**干活的方式**，不只是规格。所有写代码/改配置/跑构建的工作（开发/前端/后端，PMO 补位同守）：

1. **环境自检先行**：动笔前真实确认运行环境——`python --version` / `node --version` / 依赖装没装 / 端口占没占 / 双击路径能不能打开；拿不准就先跑通最小验证（hello 级别）再写业务。
2. **小步真跑**：每完成**一个可运行单元**（一个页面/一个路由/一个处理步骤）就真实运行——起服务请求一遍、开页面点一遍、造样例数据跑一遍，看真实输出再继续下一个单元。**禁止"一口气盲写全部再祈祷能跑"**——那是 bug 攒大爆炸，返工成本翻倍。
3. **读输出，不猜**：不符合预期时先读**完整**的错误信息与真实输出（日志/响应/截图），定位到具体行再改；**连续盲改 2 次必须停下来先看真实输出**——瞎试不是调试，是烧 token。
4. **改一处验一处**：每次修改后重跑受影响的**最小验证**，不攒一批改动一起验；牵连多点时逐点验。
5. **构建与产物执行**：构建命令真实执行、产物真实打开验证（dist 经启动方式真的能打开、页面真的渲染），构建失败读完整日志定位，不清空重跑碰运气。
6. **过程留痕**：关键运行的真实输出（成功与失败**各至少一条**）摘录进 06「自审记录」——这是证据链，不是流程仪式。
7. **长任务分段**：多步的活先列步骤清单（积木块/Todo），逐步执行逐步打勾，不跳步、不并行改互相关的点。

**执行红线**：盲写不跑 = 交稿自查不过；"应该能跑 / 理论上没问题" = 禁词——要么真跑过，要么明写"未验证 + 原因"。
