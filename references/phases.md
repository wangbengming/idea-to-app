# 流程编排手册（五阶段 + 探索模式 + 持续迭代）

本手册是 SKILL.md「阶段地图」的展开：**进入某阶段前读对应节**。各关注点的深度规则在各自手册——类型差异见 `project-types.md`、角色与派工见 `team-roles.md`、设计见 `design-craft.md` + `design-baseline.md`、技术选型见 `tech-recipes.md`、执行纪律见 `execution-craft.md`、话术见 `phrasebook.md`、部署见 `deploy-recipes.md`——本文只管"何时、谁、干什么、过什么门"。

**小项目快速通道（small 编制）**：不派子代理、不打全套仪式——阶段 0 照做（复述 + 判定 + 归类），阶段 1~2 由你亲自压缩（小想法直接做保守 MVP 或一轮确认就开工），开发后 `verify` + `gate G3` + `release`。**兼岗不豁免工艺**：动笔前照 design-craft 简化五步法（气质形容词→选族→令牌抄进样板 `:root`），提测前自跑三人格对抗审查（execution-craft），有数据的项目你兼岗填 07（G4 机器校验一样要过）。探索模式与沟通铁律对任何规模都不豁免。

## 阶段 0：听懂并复述（项目经理亲自，不派工，不要让用户等流程仪式）

用自己的话讲一遍"你想要一个……的东西，它可以……"，重点复述**用途和使用场景**，结尾问"我理解得对吗？"

用户回应时立即做**确定性判定**（见下文"探索模式"）：说得出功能场景 → 正常流程；只有痛点说不出形态 → 探索模式。判定通过后顺手**归类项目类型**（对照 SKILL.md 画像表；后续 init 带 `--type`，判定依据见 `references/project-types.md`，归类后必读）——归类是你脑子里的判断，不要拿出来问用户。

## 探索模式：用户不确定自己要什么时

零经验用户经常说不清需求——他们描述的是**痛点**（"我妈老忘吃药"）而不是**方案**，而且往往要**看到东西才知道自己要不要**。对这样的用户，连环追问只会得到"都行""你看着办"。原则：**从"问"改为"给"**——给方向、给样品、给默认值。

**判定（阶段 0 复述后立即做）：**

| 用户状态 | 典型信号 | 动作 |
|---|---|---|
| 清晰 | 说得出功能和场景 | 正常流程 |
| 半清晰 | 有痛点、说不出形态；回答笼统犹豫 | 探索模式三步（下述） |
| 模糊 + 小工具 | "整个啥都行"但场景很简单 | 直接做保守 MVP——只留 1 个核心动作，先让用户摸到真东西，需求从真实使用里浮现 |
| 模糊 + 影响大 | 痛点大、方向多、牵扯家人/钱 | 探索模式完整走，方向锁定前不 init、不开发 |

**三步法：**

1. **痛点翻译**：把痛点翻译成 2~3 个不同的解决方向，每个方向讲一段"一天的使用"（话术见 phrasebook）。方向之间要有**真实差异**（如：自己打卡 / 应用到点提醒 / 家人远程可见），不是同一件事的三种说法。
2. **方向选择**：用 AskUserQuestion 让用户挑。选不出、且是中型以上项目 → 做**样品**：每个方向一张单文件假界面（只能看、不存数据），做完执行 `probe <样品.html> --label "方案A-大按钮"` 打上"样品"横幅并归档到 `探索/`，用户双击就能点开感受，不用装任何东西。样品小项目你亲自做，中型以上派设计师（写入其派工单）。**发给用户时必须嘴上说明"这是样品，用来看方向，不是成品"**——横幅是兜底，说明是主责。
3. **锁定回主流程**：用户选定后，把方向与理由摘录进《我的应用.md》，`init` 进入正常五阶段流程。探索产物全部留在 `探索/` 归档，**不做门禁**——样品本来就是用来扔的；选定方向的样品截图作为设计阶段的画像输入。迭代期（已发版）的小探索同样走 `探索/` 与 `probe`，选定方向后落成变更提案（`propose`）回主流程。

**默认值策略**：探索期间所有拿不准的细节，由你选一个保守默认并明确告知："价格怎么记我先按'大按钮选大概数'做，用着不顺随时改。"决策负担留给团队，不留给用户——零经验用户要的不是被问倒，而是"有人替我拿主意，但我能改"。

## 阶段 1：分析拓展 + 总体规划（产品经理出活，项目经理翻译）

中型以上：`init` 建项目 → `dispatch pm` → 补齐占位（用户原话逐字 + 你的复述；派工单已自动附方法手册绝对路径与交稿自查三问，保留勿删）→ 派子代理填 `01-PRD` → `gate G1`。过门后把 PRD 翻译成大白话需求清单给用户确认。类型增量（派工单会自动携带，你补占位时也要带上）：**data 项目必须拿到输入文件样例、问清输出去向**；**admin 项目必须逐格确认权限矩阵（谁能看、谁能改）**；**front 项目必须列素材清单（文字图片谁提供、何时给）**。

需求确认后，产品经理接着产出 **《00-项目规划书》**——把第一版拆成**积木块 M1/M2/M3…**（每块装哪些 AC、前置依赖、拼完用户看到什么），像拼乐高一样一格格排好顺序（`scaffold 00` 可落模板；G2 机器校验：覆盖全部第一版 AC、不私加需求）。你把它翻译成大白话给用户确认："第一块先拼『能记账了』，拼好你看一眼；第二块拼『能改能删』……"用户点头才开工。后续所有岗位**只按规划书依次推进**；用户中途要变，先改规划书再动工。

具体动作（小项目由你亲自做）：① 场景想象——描述 1~2 个使用片段让用户"看见"成品；② 功能分堆——**必须有/锦上添花/以后再说**，第一版只做"必须有"，主动替用户砍需求；③ 提问——一轮最多 3 个、全关于"你会怎么用"、绝不问技术、优先用 AskUserQuestion 给选项。想法很小很清楚就跳过提问；用户连问题都答不上来（"都行""你看着办"）时不要追问，转**探索模式**。

## 阶段 2：蓝图确认（设计师出方案，项目经理翻译）

`dispatch design`（输入补上用户画像：年龄、设备、特殊约束如"不识字/视力弱"）→ 子代理按 `references/design-craft.md`（商业级设计工艺手册）的**五步法**工作：风格定位（气质形容词 + 选风格族 + 认领行业反模式）→ 设计令牌（五套令牌：色彩 16 语义位/字体/间距密度/深度阶梯/动效预算，落成 `:root` 变量表）→ 布局模式（每页用成熟区块模式）→ 细节密度（组件五状态、数据四境况）→ 按优先级审计；ui-ux-pro-max 技能可用时先跑 `--design-system` 拿专业库推荐再本地化（禁外链字体→系统字体栈）；同时通读 `references/design-baseline.md` 防 AI 味基线（渐变横幅/发光/"什么都在动"是设计事故，不是现代感），填 `02-设计方案` → `gate G2`（机器校验 AC 追溯 + 各章节在案）→ 你画大白话蓝图（几个页面、每块干什么、点哪里会发生什么），明确"第一版做 XX，YY 以后"，等用户说"好"再动手。蓝图禁止技术词汇。

类型差异由模板与派工单自动带出：**data 项目没有页面**——蓝图讲"处理流程和结果长什么样"；**admin 项目**蓝图讲"后台几大块、每类角色登录后看到什么"；**front 项目**蓝图讲"每页气质与手机上长什么样"，最好先给 1~2 张风格样品（probe 流程照用）。

## 阶段 3：搭建 + 自测（技术负责人定方案，开发实现，项目经理走查）

- 技术负责人（大项目派工，中小你兼任）按 `references/tech-recipes.md` 定**架构形态、数据层、组件来源**——**开源优先**：动笔前先找成熟开源组件库/样板项目**拿来二开**（下载发行文件本地引用 + 许可证与改动点留痕，禁 CDN 外链），手搓仅当更小更稳；并**逐条核对能力边界**，遵守**现代技术栈基线**（当前主流、按实际需求最优；过时技术由 verify 机器拦截），在 03「选型说明」写明**选型原因**（结论/需求匹配点/主流与维护依据/否决项及原因 + 组件来源，G3 机器校验非空）；技术决策永远不抛给用户，但**选型原因要讲给用户听**。xl 编制拆 `dispatch fe` / `dispatch be` 前后端两岗。
- **方案提出 → 问用户意见（开工前必经）**：03 定稿后，你把方案翻译成大白话向用户汇报并征求意见，讲清四件事——做成什么样（"一个双击就能用的网页"/"店里几台电脑都能用的本地小系统"）、为什么这样对你最好、数据存在哪、怎么备份；用 AskUserQuestion 问"这样安排可以吗"（选项：可以，就这么做 / 我有顾虑）。**用户点头才 `dispatch dev`**；有顾虑 → 照实回应，能调整的改 03 再确认，涉及需求变化的退回产品经理走 PRD/规划书；用户原话记入 03「用户意见」节留痕（G3 机器校验非空；方案重大调整时重新征求并更新）。问的是"安排行不行"，不是让用户在技术选项里挑。
- `dispatch dev`：开发以对应类型样板起步实现（网页 `assets/app-template.html`、后台 `assets/admin-template.py`——登录/角色/备份已内置），填写 `06-开发自查清单`。
- **积木式推进 + 逐块查验（中型以上）**：开发按规划书顺序逐块交付。每块完成后走固定四步：① 你亲自走查该块（网页真点/脚本真跑/后台逐角色）；② 演示给用户，让用户亲手点；③ 用户点头 → `checkpoint M1 --note "用户已确认"`（机器先校验该块 AC 全部打勾）；④ 用户摇头 → **阶段性重构**：按用户想法改规划书该块（AC 变更要回改 PRD 重过 G1，走退回机制）→ 重做该块 → 重新演示。已拼好的其他块不受影响。用户明确说"不用看了"的块，`checkpoint --note` 留用户原话免验。小项目不打这套仪式，直接 G3。
- **G3 提测门——你亲自执行**：`gate G3`（含 verify 静态检查 + 自查清单 AC 追溯）通过后，走查主流程（浏览器操作只有主对话能做，**禁止派给子代理**）：网页类用 browser-use 真实点一遍；**data 类真实运行脚本**（正样例 + 至少一个坏输入）；**admin 类用每个角色真实登录走一遍**。走查姿势用"笨用户新手"人格（execution-craft）：不看说明、按直觉乱点，专门找坏（点错能不能回去、空态知不知道干嘛、连点两次会怎样），不是"确认能用"的正向过场；对照 02 的操作成本预算表逐个动作数点击。发现问题打回开发，修完重测。
- 报进度只说"你会看到什么"，不说实现动作。

## 阶段 4：安全审查 + 测试 + 发布（安全/测试出报告，项目经理发版）

- **安全审查先于测试**：有用户数据的项目（data/admin 必占，front 有表单也算）`dispatch sec`，安全与隐私工程师做**防御性代码审查**，填 `07-安全与隐私清单`（数据分级/存储传输/攻击面/隐私底线/风险与缓解）。发现"严重"级问题有一票缓发权：打回开发修复，未修复不得进 G4。有数据的小项目你兼岗填写 07（G4 机器校验一样要过）；纯计算类（`--no-data`）项目免此步。
- `dispatch qa`：子代理填 `04-测试报告`（bug 固定格式 `- BUG-编号 | 严重|一般|建议 | 标题 | open|fixed`，末尾留"待项目经理走查清单"）。类型增量：data 必含「样例数据测试 + 异常输入测试」；admin 必含「角色权限测试」（机器校验）；front 逐页查 title/空态/404，响应式列进走查清单。
- `gate G4`：机器校验无 open 的严重 bug、测试用例 AC 全覆盖、**规划书里全部积木块经用户查验（checkpoint 记录）**、**安全与隐私清单在案**（有数据的项目）、《使用说明.txt》存在、**《00-当前功能清单》在案**（首版发版前把你做出来、经用户查验的功能填进去，此后只经 release 合并更新）、本轮已过 G3。
- 发布动作由你完成：`release --note`（自动把变更增量并入《00-当前功能清单》并归档提案）+ 更新《我的应用.md》《使用说明.txt》，然后按 phrasebook 交付话术告诉用户三件事：① 双击哪个东西就能用（文件 / 启动.bat）；② 数据存在哪、怎么备份（单机=备份按钮，后台=备份数据按钮/复制数据文件）；③ 想改什么，直接用普通话告诉我。

## 阶段 5：交付与部署（竣工后，项目经理亲自）

全部积木块查验通过 + G4 发版 = **竣工**。本地已经能用，此阶段锦上添花，做不做由用户定：

1. 复习交付：确认用户会打开、会备份、有进度感（话术见 phrasebook）。
2. **给 1~3 个部署建议**（按类型，讲清好处与代价，用 AskUserQuestion 让用户挑；详见 `references/deploy-recipes.md`）：data→定时自动运行；admin→同一 WiFi 开放、自动备份、（谨慎）公网上线；front→发布到网上（静态托管，免费）、域名（花钱）。用户不采纳也完全正常，不推销。
3. **用户采纳 → 出具体方案**：写《部署方案.txt》（分步骤：点哪里、填什么、看到什么算成功），需要用户注册/操作的步骤全程带教；涉及花钱或数据放到网上的，先把后果讲清楚、用户点头再动手；安全工程师的缓解建议先落实再上线。
4. 部署完成后真实验收一遍（换台设备访问、定时任务真的触发一次），把新用法写进《我的应用.md》。

## 持续迭代（变更提案制）

竣工发版后，功能变化一律走**变更提案**（借鉴 spec-driven 的"先提案、再动工、发版合并"机制，对用户全程隐身——用户只看到大白话确认和"改好了"）；纯修 bug 不立提案，直接修 → `gate G3` → `gate G4` → `release`：

1. **复述确认**：用户反馈先复述（"你是想要……对吧？"），分清是修毛病还是要改功能。
2. **归类**：（中型以上）产品经理把新需求归"必须/以后"。"以后"的不立提案，记进规划书"以后再说"（用户催进度时温和提醒：先把手头这版用顺）；"必须"的进下一步。
3. **立提案**：`propose <变更名>`（中文短名，如"加导出"）落 `团队文档/变更/<名>/提案.md`，补齐四件事：**为什么改**（用户原话逐字）、**改什么**（大白话；砍掉/替换现有功能必须明说）、**用户确认**（点头原话，动工前拿到，G3 机器校验）、**功能增量**（对照《00-当前功能清单》：新增哪些功能、修改/移除哪些 F-编号）。一轮诉求一份提案，可以装多个变化；多个独立诉求**一次只立一份提案**（G3 机器校验进行中提案 ≤1），其余先记进"以后再说"堆，做完发版再立下一份。
4. **拼积木**：按提案「任务安排」把新需求追加为规划书新积木块（AC 变更回改 PRD 重过 G1），开发、`checkpoint` 逐块查验照常。
5. **发版即合并**：`gate G4` 通过后 `release` 自动把每份提案的功能增量**机器合并**进《00-当前功能清单》（新增追加/修改替换/移除删除），提案移入 `变更/归档/<日期>-<名>/`，变更史留一行（中型以上发版强制过 G4，小项目豁免）。**功能清单只经此路更新，不手改**——它记录"应用现在真的有什么"，新开会话接手、写交付说明、排测试都以它为准；"想加什么"在提案里，不在清单里。
6. **大白话汇报**：照发布记录讲"这次改了什么"，同步更新《我的应用.md》；用户中途反悔 → `propose <名> --drop` 归档提案，不动代码。
