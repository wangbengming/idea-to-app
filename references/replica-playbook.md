# 对标复刻手册（"做个像剪映/像XX的东西"专用打法）

用户点名复刻市面上已有的成熟产品时（剪映、美图、Excel、Notion、Flappy Bird……），普通流程会把它当"功能多一点的单机工具"做，产出一个形似而神不似的玩具。本手册给**复刻模式**的三步法、能力速查与验收标准。**阶段 0 识别到复刻信号即读本册**；类型照常归（tool/data/admin/front），复刻是叠加在上面的模式。

## 立场（先对用户想清楚，再对用户说清楚）

- 剪映是几百人团队做了很多年的产品。**复刻 ≠ 克隆全部**：我们复刻的是"**你的场景里真正会用到的那条核心链路**"，标准是量化指标达标、用起来顺手，不是界面上长得像。
- 复刻项目天然是 medium 起步（核心链路本身就是 ≥3 个功能），别按 small 走快速通道。
- 对用户的说人话定位（phrasebook 风格）："剪映那种全家桶咱们不比——你主要用它做 X 和 Y，我把这两步做到跟它一样顺手，其他的不做。"**边界先讲明，做出来才不"差强人意"**——复刻落差的一半是期望没管住。

## 第一步·标杆拆解（产品经理，写进 PRD「同类调研」）

同类调研在复刻项目里**升级为标杆拆解**，三样东西缺一不可：

1. **功能全景清单**：用 WebSearch 查标杆的官方帮助文档/功能列表/评测文章，把功能逐条列全（别凭印象写"大概有这些"）——列全了才知道砍什么。
2. **量化体验指标**（复刻的命根子，直接进 AC）："专业级手感"翻译成数字——
   - 流畅度：预览/播放帧率（如 ≥24fps）、拖动跟手延迟（如 ≤100ms）；
   - 响应：点击到画面变化 ≤1 帧/≤100ms、操作无卡顿（连续操作 10 次不掉帧）；
   - 耗时：导出 1 分钟 1080p 视频 ≤N 分钟、处理 100 张图 ≤N 秒；
   - 手感细节：标杆的快捷键、默认参数（默认字幕字号/转场时长）、微交互（拖拽吸附、磁性时间线）——查不到就实测标杆产品记录。
   测得到的自己测，测不到的查评测数据并附来源；实在没有写"未查到，按 X 估算"。
3. **场景访谈**（只问使用习惯，技术问题不上问桌）："你现在用剪映最多的是哪两步？哪一步最烦？"——答案决定核心链路。

## 第二步·场景裁剪（产品经理 + 用户确认）

1. **核心链路只留 1 条**：如剪映 → "导入 → 粗剪（分割/删除/排序）→ 配字幕 → 导出"。链路上的每一步都对齐标杆的量化指标；链路外的全砍。
2. **功能对标矩阵**（PRD 必含，G1 评审看它）：

   | 标杆功能 | 本版 | 说明 |
   |---|---|---|
   | 时间线拖拽剪辑 | ✅ 做 | 对齐指标：拖动跟手 ≤100ms |
   | 自动识别语音生成字幕 | ⭕ 简化 | 手动输入字幕，自动识别列"以后再说"（原因：本地轻量做不到准确率） |
   | 多轨合成/画中画 | ❌ 不做 | 单轨足够本场景；需要时属版本升级 |

   "不做"的每格要给**替代路径**（用回原产品的那一步/以后再说），不是留白。
3. **边界声明**（对用户，大白话）：做到八成像的是哪条链路、哪几个指标对齐了、哪些做不到为什么。写进 PRD 与交付说明。

## 第三步·技术对标（技术负责人，写进 03）

### 重计算/多媒体能力速查（复刻项目的选型第一站）

**开源同类实现研究（核心交互呆板的根治法，必做）**：核心交互——时间轴、画布、轨道、拖拽列表这类"手感就是产品"的部分——**不许凭直觉从零手写**。动笔前先找 2~3 个**开源同类实现**（宽松许可证）研究它们是怎么做到的：渲染方式（canvas 分层/脏矩形重绘）、数据结构（片段列表还是树、帧对齐怎么算）、关键算法（吸附/缩放变换/撤销栈），能拿来二开的直接拿来二开过开源四关；确要自研，03 里写明"从哪个开源实现学了什么"——研究过的自研和没研究过的自研是两种东西，后者产出的就是呆板时间轴。为什么商业编辑器的时间轴是那种效果：它不是 DOM 拼的格子，是 canvas 逐层绘制的帧视图 + 独立播放时钟 + 代理预览——照着实现路径做，才可能接近那种手感。

| 要做的能力 | 该用的轮子 | 备注 |
|---|---|---|
| 视频解码/编码/转码 | **WebCodecs**（浏览器原生，快）优先；兼容兜底 **ffmpeg.wasm** | ffmpeg.wasm 体积 25MB+ 且是 **LGPL** 许可——能过"宽松许可证"关的前提：不改库本体、动态引用、03 留痕注明；或选 MIT 系封装（mp4 容器读写库等）+ WebCodecs 组合，逐个过开源优先四关 |
| 逐帧渲染/特效合成 | canvas 2D；性能不够 → WebGL | 时间线/帧预览用 canvas 自绘 + requestAnimationFrame，别用 DOM 拼时间线 |
| 音频处理 | Web Audio API | 标准 Web 能力，零依赖 |
| 图像批处理/滤镜 | canvas；大图流水线 WebGL shader | —— |
| 3D 场景 | Three.js（MIT）本地引用 | 引入阶梯 L2 能力库 |
| 语音识别/AI 生成类 | 第一版不做，或明确降级 | 本地跑不准、联网违背自包含——诚实列入"不做"并给替代 |

这些属于引入阶梯的 **L2 能力库**：体积大（十 MB 级）是这类能力的正常成本，不算违背"轻交付"——但**必须真实测过性能再定**，不许"应该能跑"。

### 形态适配（重计算项目最常翻车的一步）

- **视频/音频/大型媒体处理默认形态 E（本地服务）**：localhost 环境解锁 worker、多线程 wasm、SharedArrayBuffer（需在服务响应头加 COOP/COEP，写进 03 与骨架改造点）；文件读写走本地服务也远快于浏览器沙箱。
- **轻量处理可用形态 B（文件夹网页）**：WebCodecs/canvas 在 file:// 下可用，但 worker 受限——先做技术验证样品（探索/probe），跑得动再定形态。
- **形态 A（单文件）不适合媒体类复刻**：能力库体积与 worker 限制决定了塞不进单文件——选 A 不是省事，是自废武功。

### 性能预算（03 必须写死，验收照此判）

复刻项目的性能预算不是"列表 >1000 条分页"，而是第一步拆出来的量化指标逐条落位：每条指标写"目标值 + 怎么测 + 不达标怎么降级"。降级的合法姿势：实时做不到 → "**粗预览 + 精导出**"（预览用低码率代理，导出用全量渲染），对用户说明这不是缩水而是行业通行做法（剪映也用代理预览）。

## 验收（复刻到位的判据）

1. **功能对标矩阵**全链路 ✅；2. **量化指标**逐条实测达标（QA 用例=指标实测，写数据不写"流畅"）；3. 规划书最后一块是**手感打磨**（快捷键/默认参数/微交互对齐标杆）；4. 交付时给用户**差距清单**："与剪映相比，我们做到的是 A/B/C，做不到的是 D/E（原因），需要时你可以……"。
